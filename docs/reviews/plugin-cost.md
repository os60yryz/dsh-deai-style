# 这个插件让每次请求贵了多少

用户问「会不会翻倍消耗」。不估，直接量：用固定前缀做对照，读 API 返回的 `usage.prompt_tokens` 算差额；再拿本机 12 个会话的真实记账做分母。

复现：`node tests/measure_plugin_cost.mjs`、`python scripts/session_token_stats.py`。

## 一、固定开销（每次请求都带）

| 项 | 字符 | token |
| --- | --- | --- |
| 系统提示段（strict，含工具提示行） | 861 | 542 |
| `deai_scan` 工具 schema | 309 | 330 |
| 合计 | 1170 | **872** |

改前是 932（工具 schema 390）。省下的 60 来自把描述从三句压成一句。

两个细节值得记：中文约 0.63 token/字符，而工具 schema 是 1.07 token/字符——JSON 的键名和括号比中文贵。所以省工具描述比省提示词划算。

## 二、真实记账（12 个会话、983 次模型请求）

| 口径 | 数值 |
| --- | --- |
| 未命中缓存输入 | 中位 268，均值 3109 |
| 命中缓存读取 | 中位 112,128 |
| 有效输入（缓存按 0.1 倍折算） | 中位 12,762，合计 13,836,313 |

插件那 872 token 坐在系统提示的稳定前缀里，从第二次请求起走缓存价。

- 摊到每次请求：约 **86 等价 token**。
- 占有效输入：**0.62%**。
- 唯一按全价付的场景是每个新会话的第一次请求，多付 872。

所谓「翻倍」不成立：插件自己是千分之几的量级。

## 三、工具调用一次的开销

`deai_scan` 的往返 = 正文原样回传 + 报告返回。对一段 103 字的 AI 腔样例：入参 47 token，报告 300 token——报告是正文的 4.8 倍（字符）/ 6.4 倍（token）。

已改成精简报告：同一段样例 491 字符 → 194 字符，300 token → 106 token，**省 65%**。完整报告（带逐条样例）保留给人类和 CLI，工具返回只给分数、命中的规则 id、以及最多 3 条建议。

调用频次：983 次请求里 4 次（0.4%）。这个窗口里插件才刚上线，样本不算数，但它至少说明工具不是每次回答都触发的东西——所以真正贵的是那 330 token 的常驻 schema，不是调用本身。

## 四、还能怎么省

| 做法 | 每次请求省 |
| --- | --- |
| `level: "soft"`（少 5 条 strict 补充条款） | 118 |
| `injectLintTool: false`（不注册工具，也就没有 schema） | 330 |
| 再去掉 `maxSuggestions` 参数 | 39 |

三个都做是 872 → 485。默认没改：`soft` 档少了五条实际生效的规矩，`injectLintTool: false` 等于砍掉插件最有用的一半（模型能自己查），这两条是产品取舍，不该由「省 token」单方面定。要省就在 profile 里显式配。

## 五、被锁住的量

`tests/checks.mjs` 第 17 组盯着三件会悄悄膨胀的事：提示段 ≤900 字符、工具参数 ≤2 个、精简报告至少比完整报告短一半。这三条是回归门禁，不是建议——改一句话让提示段胖 20%，测试会红。
