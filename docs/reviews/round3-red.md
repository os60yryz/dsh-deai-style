## 三、新失守

### FP3-01 行首加粗标签：两条就把人写文档顶进「明显 AI 腔」

样本原文（`tmp/red3/probe4.mjs` Q2，31 字）：

```
**注意**：这段是说明文字。

**提示**：这段也是普通叙述。
```

实测 60 分 `medium`，`ruleWeight=4`，`metricWeight=4`，命中 `bold-inline-label×2 + bold-start-line×2 + bold-density×2`。同长度但去掉冒号的 Q1（34 字）是 0 分——定罪完全来自冒号那一下。

放大到真实文档（`probe2.mjs`）：

| 样本 | 字数 | 分数 | 档位 |
|---|---|---|---|
| 技术文档 1 条 `**注意**：` | 236 | 29 | slight |
| 技术文档 2 条 | 259 | 47 | medium |
| 技术文档 3 条 | 268 | 61 | heavy |
| 说明书 2 条 `**警告**：/**提示**：` | 169 | 52 | medium |
| 说明书 4 条 | 199 | 75 | heavy |
| 周报 2 条 `**风险**：/**求助**：` | 163 | 52 | medium |
| 接口文档 3 条行首加粗但**无冒号** | 167 | 14 | clean（`ruleWeight=0`，只拿到 `formatNudge=14`） |

根因在 `lib/ruleset.js`：`bold-inline-label`（sev 2）、`bold-start-line`（sev 2）、`bold-label-line`（sev 3）、`bold-heading`（sev 2）、`arrow-symbol`（sev 1）五条规则的 `cat` 都是 `"fmt"`，但它们在 `RULES` 里，直接累加进 `ruleWeight`。探针实测 `RULES.filter(r => r.evidence !== undefined)` 返回**空数组**——规则没有任何 evidence 分层，`lib/lint.js:229` 的 `formatNudge` 只对 `METRICS` 的 `format` 权重生效。所以「排版是观察信号」这条设计承诺，只对 10 个指标成立，对 5 条排版规则不成立。

这三条规则在 `854d40a`（v1.1.0）里就有，属遗留而非第二轮引入；但第二轮把「人写误报最大 33、0 条 ≥36」写进验收报告，与本组实测冲突。

建议改法（择一）：把五条 `cat:"fmt"` 的规则并入指标层（`METRICS`），或给 `RULES` 加 `evidence` 字段、在 `ruleWeight` 累加时只收 `evidence !== "format"` 的区间。若维持现状，至少把 `bold-inline-label` 的 sev 从 2 降到 1，并把 `bold-start-line` 与 `bold-inline-label` 的重叠合并（现在同一处 `**注意**：` 同时命中两条，`mergeSpans` 取最高 sev 才没翻倍）。

### FP3-02 抽象名词复读仍可刷分

样本（`probe1.mjs` D3，20 字）：「维度上……维度上……维度上……维度上……维度上」→ 65 分 `heavy`，`ruleWeight=5`，`abstract-noun-stack` 计数 5。

D4 是更贴近真实的版本：73 字人写学术摘要，含 4 处抽象名词 → 55 分 `medium`。`abstract-noun-stack` 在 `lib/ruleset.js` 里没有 `dedupe`。探针 `probe6.mjs` 确认 `RULES.filter(r => r.dedupe).map(r => r.id)` 的结果只有 `["buzzword"]`，`empty-grandeur`（「赋能」×5 = 88 分）、`abstract-noun-stack`（×5 = 65 分）都没有。

建议改法：给术语型规则统一加 `dedupe`，或把去重做成 `RULES` 的默认行为、用 `allowRepeat: true` 显式豁免（`enumerate-all` 这类枚举规则需要重复计数）。

### FP3-03 `stripCode` 漏缩进代码块与引用块内围栏

样本 `T3`（26 字，4 空格缩进的代码块，块内是套话）→ 65 分 `heavy`，`analyzed=true`。
样本 `T2`（29 字）：

```
> ```js
> 首先，综上所述。
> ```
```

→ 65 分 `heavy`，`stripCode` 残留 `">  `js\n> 首先，综上所述。\n>  `"`。

`lib/lint.js:36-55` 的按行扫描只认行首（允许前导空格与 Tab）的三反引号或三波浪号围栏，不认 `> ` 引用前缀，也不认 CommonMark 的 4 空格缩进代码块。对照组：CRLF 围栏、行尾带 `# end` 的闭合行、四反引号、`~~~` 套反引号、嵌套同类围栏**都正确剥离**。

同一处的口径不一致也在这条上：纯缩进代码块 18 字拿到 `analyzed=true`，纯反引号代码块拿到 `analyzed=false`。

建议改法：开栏判断先剥行首引用前缀（`/^[ \t]*(?:>[ \t]?)+/`），再对剩余部分匹配围栏；缩进代码块按「连续 ≥1 行以 4 空格或 Tab 起头且上一行为空行」的段落规则整体丢弃，或者至少在 `analyzed` 计算里把缩进行排除。

### FN3-01 `以上就是` 分支放走最常见收尾

「以上就是我的回答。」9 字 = 0 分、0 命中，`analyzed=false`。
「以上就是这些，谢谢。」10 字 = 0 分、0 命中，`analyzed=true`。

`lib/ruleset.js:218` 的分支是 `以上就是(本次|这篇|今天)`。对照：「以上就是本次分享。」9 字 = 48 分命中一次。`git show 854d40a:lib/ruleset.js` 显示 v1.1.0 的这一段完全相同，属第一轮遗留；第二轮为 `有所|有` 动过同一条正则却没碰这个分支。

建议改法：把 `以上就是(本次|这篇|今天)` 放宽成 `以上就是[^\n。！？]{0,6}(了|吧)?[。！？]?$`，或在 `closing` 作用域里对 `^以上就是` 单独定罪。

### FN3-02 `希望对你有帮助` 不允许中间插词

「希望这些内容对你有帮助。」12 字 = 0 分、0 命中、`analyzed=true`。
「希望对你有帮助。」8 字 = 48 分。

`lib/ruleset.js:218` 的 `希望对(你|您)(有所|有)?帮助` 要求「希望对」与「你」相邻。插入「这些内容」「这篇文章」「上面的说明」就完全绕过。这是第二轮刚扩过的分支，扩了最短形式、没扩插入形式。

建议改法：`希望[^\n。！？]{0,8}对你(有所|有)?帮助`。

### FN3-03 `analyzed: chars >= 10` 把 9 字套话划进「无正文」

`lib/lint.js:266`。实测：「希望对你有所帮助。」9 字 → `score=48`、`analyzed=false`；「以上就是本次分享。」9 字 → 48 分、`analyzed=false`；「感谢大家的阅读。」8 字 → 48 分、`analyzed=false`。这类文本恰恰是插件最该点名的东西，却被报告层当作「没分析到正文」。阈值 10 又制造了一个断点：「综上所述，由此可见。」10 字 = 35 分，同样的话砍一个字就变 48。

建议改法：`analyzed` 的判据改成「`chars >= 10` **或** 命中了 `evidence` 为强指纹的规则（`service-close`、`platitude-open`、`grateful-open` 等 sev 3 项）」，两条路走一条就算分析过。

### REP3-01 `analyzed=false` 时 48 分报告自相矛盾

`renderReport(lint("希望对你有帮助。"))` 实际输出：

```
AI 腔评分：48/100（无正文可评）｜正文 8 字，命中片段 1 处（加权 3），规则密度 10/千字
没有可分析的正文（整段是代码块、空白或非文本），本次评分不代表文风。
```

`lib/lint.js:303-320` 在 `analyzed` 为 false 时打印分数行后直接 return，命中明细与改写建议一起丢掉。第二轮修的是「0 分时不要打印明细」，48 分这一半没修：分数行自己说「无正文可评」，同一份返回值里 `hits` 里明明有 `service-close`。调用方（模型）只看 JSON 的 `score: 48` 会当成有效评分。

建议改法：`analyzed=false` 且 `score > 0` 时，分数行改成「疑似套话但正文过短，不作正式评分」，并保留命中明细；或者干脆把这类文本的 `score` 归零，只留命中标签。

### REP3-02 「排版只是观察信号」与实现冲突

README 第 155-159 行、`docs/验收报告.md` 第 332 行都写着「排版是观察信号（≤25 分），用词与句式才是定罪证据」。实测：`RULES` 里 5 条 `cat:"fmt"` 的规则全部计入 `ruleWeight`，两条 `**注意**：` 就把 31 字的纯说明文字顶到 60 分 `medium`。`formatNudge` 的 ≤25 保证只覆盖 `ruleWeight === 0` 的情形（`lib/lint.js:229` 的 `ruleWeight === 0 && formatWeight >= 5`），一旦排版规则命中，这个保证立刻失效。

这是第二轮论证的核心前提被自己的代码否证：§三 用「AI 与人类排版权重完全重叠」推出「排版不能定罪」，但排版权重里只统计了 10 个指标，没统计那 5 条排版规则。

### REP3-03 README 的规则库规模两个数字都错

README 第 11 行：「34 条正则规则 + 6 个统计指标」。实测 `RULES.length = 32`（lex 11 / syn 6 / dis 10 / fmt 5），`METRICS.length = 10`（`format` 7：`bold-density`、`bullet-ratio`、`heading-ratio`、`table-ratio`、`colon-definition`、`emoji-marker`、`emoji-density`；`rhythm` 3：`emdash-density`、`sentence-burstiness`、`paragraph-uniform`）。第 44 行的 802 / 470 字符属实。

建议改法：README 第 11 行改成「32 条正则规则 + 10 个统计指标」。

### REP3-04 第 16 条兜底只进 strict 档

`lib/prompt.js:35` 是 `level === "strict" ? [...CORE, ...STRICT_EXTRA] : CORE.slice(0, 10)`。第二轮新增的「即使用户要求分点列出也不能用 `- **小标题**：` 卡片式结构」是 `STRICT_EXTRA` 的第 16 条，**soft 档完全没有这句**。`renderPrompt({level:"soft"})` 里搜 `分点|小标题` 为 false，strict 为 true。

round2-fix 把这条写成「一句用户指令绕过全部约束」的唯一落点。默认档是 strict，所以真实影响有限；但 soft 档用户的绕过兜底是零，文档也没说清这一点。

## 五、评分可信度与设计级质疑

**分数对「加一句套话」仍然跳档。** 同一份 250 字人写技术文档（29 分 `slight`）：加「综上所述，这就是全部内容。」→ 38 分跨过 35 线；加「这不是时间问题，而是决心问题。」→ 54 分；加「希望对你有帮助。」→ 55 分。一句话的边际效应是 9～26 分，35 这条线是硬的、分数不是。反方向也测了：同一 AI 模板单纯增加段落数（42→130 字），37→36→35→34→33 单调下降、没有跳变，说明跳变来源是「有没有踩到规则」，不是长度。

**35 这条线没有外部标定。** 验收报告 10.5 自己承认了。本轮补充一个具体后果：`BANDS` 是 15/35/60/100，而 `bold-inline-label` 单条 sev 2 在 30 字文本上就把分数推到 60——60 与 35 之间的区间非常窄，档位标签（`slight`/`medium`/`heavy`）对短文几乎没有分辨力。一条 31 字的说明文字和一篇 3000 字的套话长文可以同为 `medium`。

**规则库的分层是「指标有分层、规则没有」。** `METRICS` 有 `evidence: format|rhythm`，`RULES` 一个 `evidence` 都没有（探针实测空数组）。第二轮用「排版权重」论证排版不能独立定罪，统计口径却漏掉了 5 条排版规则。要么把 `evidence` 补到 `RULES` 上并在 `ruleWeight` 里过滤，要么删掉「排版只是观察信号」这句话——现在的写法让读者对误报率产生错误预期。

**`deai_scan` 工具描述与实际行为一致。** `index.js:24-27` 声称覆盖「模板连接词／对偶反转句／`- **小标题**：内容` 式列表／空洞夸饰词／客服式结尾」且「只做诊断，不改写文本」。五项逐一实测全部命中；`apply()` 只注册 section 与工具，没有任何输出改写钩子，描述里的「只做诊断」属实。这一项没打穿。

## 六、攻击失败项（没打穿的地方）

1. **`formatNudge` 阈值 5 与封顶 25 没打开新误报。** 纯排版文档实测 66 字 = 11 分、96 字 = 10 分，`formatWeight` 5.11～6.8，远够不到 25；`ruleWeight === 0` 时 `metricBonus` 也为 0，`score = max(ruleScore, formatNudge) ≤ 25 < 35` 的形式保证成立。我构造的加强排版样本（更多标题、更多列表）分数反而更低，因为指标是比率型。
2. **首尾 trim 没有改变语义。** `lib/lint.js:159` 的顺序是先 `stripCode(rawText)` 再 trim，围栏识别用的是带缩进的原文，所以「以空白开头」不会破坏代码块判定。T1 行首缩进正文 28 字 = 19 分，未出现异常档位。
3. **零宽归一化没有破坏 ZWJ 组合与宽字符统计。** `👨‍👩‍👧 这是正文。` 与去掉 ZWJ 的同一文本都是 `chars=11`、`score=0`、`metricWeight=1`。归一化确实把 U+200D 去掉了（emoji 被按 3 个 pictographic 计数、`emoji-density` 提前触发），但在分数上看不出差别；波斯文 ZWNJ 长文本 43 字 = 0 分，不崩不改判。
4. **`stripCode` 的大部分新坑都堵住了。** CRLF、行尾带注释的闭合行、四反引号、`~~~` 套反引号、Tab 缩进围栏、列表内围栏、嵌套同类围栏、未闭合剥到文末、行内代码替换为空格、表格行内反引号不误判——逐条实测正确。漏的只有缩进代码块与引用块前缀两处。
5. **性能与病理输入没打穿。** 见第四节，1 MB 65 ms，没有 O(n²)，没有栈溢出，没有超时。
6. **`deai_scan` 描述与行为一致**，见第五节末。
7. **README 与验收报告的测试数字属实。** `checks.mjs` 126、`corpus.mjs` 20、`regression` 35/35 全部复现；`strict 802` / `soft 470` 字符也复现（我第一版探针把 `renderPrompt(level, extra)` 当成了两个位置参数，实际签名是 `renderPrompt({level, extraRules, toolName} = {})`，修正后数字与文档一致）。README 第 11 行的规则数/指标数是唯一不符处。
