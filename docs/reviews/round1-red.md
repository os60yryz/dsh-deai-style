## 一、结论速览

**失守 12 条**：误报（人写中文 ≥36 分）4 条，漏报（明显 AI 腔 ≤20 分）8 条。规则级缺陷 14 条，设计级问题 5 条。

最严重三条：

1. **纯人写的 278 字中文随笔得 43 分（中等 AI 腔）**。全文没有一个 AI 腔词、没有模板连接词、没有对偶反转、没有加粗列表，分数几乎全部来自 `sentence-burstiness` 与 `paragraph-uniform` 两个统计指标——**文字写得越工整，越被判成 AI**。按插件自己写在系统提示里的规则（"分数高于 35 时，按命中项重写"），这段文字会被要求重写。
2. **判定结果由文本长度决定，不由内容决定**。同一段 AI 腔文字，58 字得 57 分，接 2040 字中性叙述后 25 分，接 5440 字后 16 分，接 10200 字后 13 分（"基本没有 AI 腔"）；命中的规则一条没少。规则密度除以字数，长文（公文、报告、长回答）实际上等于免检。
3. **纯表格回答得 0 分**。`stripCode` 把 Markdown 表格整体替换成空格，表格型回答 `chars=0`、`score=0`，`renderReport` 输出"未命中任何规则"。同类剥离问题还有未闭合代码围栏：` ``` ` 没闭合时代码正文被当散文打分，一段含注释的 JS 得 54 分。

攻击失败项（如实记录，见 §四.15 与 §六.3）：`g` 正则 `lastIndex` 复用、灾难性回溯、开关零注册语义、已装副本与源码一致性——都没打穿。

## 四、规则级缺陷

每条给出：位置 → 复现输入 → 期望 vs 实际 → 严重度 → 修复建议。全部实测于 `tmp/red1/out2.json` / `out3.json`。

**1. `ruleScore` 的密度归一化方向错误（最严重，全局）**
`lib/lint.js:107` `const density = (ruleWeight * 1000) / Math.max(m.chars, 300);`
复现：`probe3.mjs` 的 `thin` 组。同一段含 `标志性`+`作为一个…，`+`一般来说` 的文字，后面接 0/30/80/150 组中性叙述：

| 全文字数 | 58 | 2098 | 5498 | 10258 |
|---|---|---|---|---|
| 分数 | 57 | 25 | 16 | 13 |
| 命中规则 | 3 条 + 0 指标 | 3 条 + 1 指标 | 3 条 + 1 指标 | 3 条 + 1 指标 |

期望：追加无关文字不应改变原有段落的判定。实际：分数随总字数单调下降，10258 字时该段落被判为"基本没有 AI 腔"。**严重度：高**。建议：按段落/句子窗口计算密度再取最大值或分位数，而不是全文平均。

**2. 规则计数饱和 `Math.min(h.count, 2)`**
`lib/lint.js:103`。复现：FN-09 中 `transition-cliche` 实测命中 90 次，权重贡献 `2×min(90,2)=4`；把 90 次减到 2 次，分数不变。
期望：30 倍频次的模板词应显著加权。实际：完全饱和。**严重度：高**。建议：改为 `min(count, K)` 且 K 随文本长度缩放，或对高密度规则单独设阈值。

**3. 结构指标加成封顶 10 分，却足以单独把中性文本推过 35 线**
`lib/lint.js:109` `math.min(10, metricWeight*1.5)`。复现：HUMAN-LONG（278 字人写随笔，`ruleWeight` 仅 3）得 **43 分**，其中约 10 分来自 `sentence-burstiness`(1.26) + `paragraph-uniform`(1.43)。
期望：没有词汇/句法 AI 腔证据时不应越过合格线。实际：两个纯统计指标即可推人写文本到"中等 AI 腔"。**严重度：高**。建议：结构指标只在已有规则命中时作为加成，或把"无人写 AI 腔词"的文本限制在 ≤15 分。

**4. `significance-filler` 把"标志性"当成 3 级 AI 腔**
`lib/ruleset.js:27` 正则 `标志(着|性)`。复现：`"外滩是上海最标志性的地方"` → 单条命中即 33 分（300 字下限下）。"标志性建筑""标志性时刻"是正常汉语。
期望：只匹配"标志着/见证了/开启了"这类套话。实际：把形容词误伤。**严重度：高**。建议：删掉 `性` 分支。

**5. `translationese` 把"作为一个…，"列进 3 级**
`lib/ruleset.js:55` `作为一个[^。，；\n]{0,8}[，,]`。复现：`"作为一个中年人，我不觉得…"`（FP-01 组成部分）、`"作为一个父亲，他其实没什么大道理可讲"`。
期望：`作为一个` 是正常汉语介词结构（= 身为）。实际：`sev3` 命中，短文里固定 33 分。**严重度：高**。建议：整条从正则里移除。

**6. `colon-definition` 行首匹配过宽，误伤正文冒号句与时间**
`lib/ruleset.js:148` `/^(?![^\n]*\*\*)[^\n：:]{4,24}[：:]\s*\S/gm`。复现：`"上午十点开始14:30结束，大家别迟到"` → 命中（时间里的冒号）；HUMAN-LONG 里 `"后来我发现，她有自己的办法：把密码写在存折夹层里"` → 命中 2 次（正文一句里的冒号，因为整段只有一行，行首就是段首）。
期望：只匹配"短标签 + 冒号 + 解释"的说明书式行。实际：任何行首 4–24 字后出现冒号都算。**严重度：中高**。建议：要求冒号后是行尾或短解释（≤20 字），并排除 `\d{1,2}:\d{2}`。

**7. 加粗类规则三重计分**
`lib/ruleset.js:236/244/257`。复现：`"- **核心结论**：效率提升的关键在于减少无效沟通，先把话说清楚。"`（33 字）→ `bold-label-line(sev3) ×1` + `bold-inline-label(sev2) ×1` + `bold-density(sev2) ×1.11`，再加 `bullet-ratio` 与 `explainer-frame`，**合计 64 分**。
期望：同一处格式只计一次。实际：一处加粗被三条规则各扣一遍。**严重度：中高**。建议：`bold-inline-label` 排除行首已被 `bold-label-line`/`bold-start-line` 捕获的位置。

**8. 同一短语被多规则重复计分**
复现：`"综上所述，这件事没有第二选择。"`（15 字）→ `summary-close(sev3)` + `transition-cliche(sev2)` = **45 分**。"首先，…其次，…"同样同时落进 `transition-cliche`，而"综上/总之"两头收。
期望：重叠规则去重或降权。实际：双重扣分。**严重度：中**。建议：建立规则互斥表。

**9. `emoji-marker` 白名单只有 10 个码点，且判定标准不自洽**
`lib/ruleset.js:162`。复现：`"😅 有点尴尬，🎉 总算完成了，📊 数据在这。"` → **0 命中**；`"❤️ 很喜欢⚠ 注意✨ 闪亮✅ 完成"` → 命中 3 次（`\uFE0F` 变体选择符被单列在字符类里，所以 `❤️` 命中而 `❤` 不命中）。
期望：识别"用 emoji 当条目符号"这一格式特征。实际：只认 10 个硬编码 emoji，漏掉绝大多数；同时对带 VS16 的任意符号误判。**严重度：中高**。建议：改为 Unicode 属性类 `\p{Extended_Pictographic}`，并按"是否位于行首/列表标记位"区分。

**10. `let-us` 的前瞻把最常见形式排除**
`lib/ruleset.js:141` `/让(我们|咱们)(?=[^\p{Script=Han}])/gu`。复现：`"让我们，一起把这个事办了吧。"` → 命中；`"让我们一起来把这个事办了吧。"` → **0 分**。
期望：抓 Let's 直译。实际：只抓后面跟标点的畸形变体，真正在用的形式漏掉。**严重度：中**。建议：删掉前瞻。

**11. `not-x-but-y` 的字符类排除分号与句号，两个常见变体全漏**
`lib/ruleset.js:99`。复现：`"不是能力不够。而是方法不对。"` → 0 分；`"效率的关键不是做得更快；而是做得更少。"` → 0 分；`"问题不是「能不能做」，而是「值不值得做」。"` → 33 分（对照，能抓）。
期望：语义上等价的反转句式应同分。实际：靠标点区分，句号/分号变体免检。**严重度：中高**。建议：把 `[^。！？；\n]` 放宽为"最多跨一个标点"。

**12. `stripCode` 把表格整体删空**
`lib/lint.js:20` `.replace(/^\s*\|.*\|\s*$/gm, " ")`。复现：FN-01 → `chars=0`、`score=0`、`hits=[]`。
期望：表格是格式指纹，应计入（至少计入 `contentLines`/`bulletLines` 或单独的 table-ratio 指标）。实际：整段消失，纯表格回答完全免检，混合回答里的表格信息也一并消失。**严重度：高**。建议：表格不删，改成把 `|` 与分隔行归一化后参与统计，并新增 `table-ratio` 指标。

**13. `stripCode` 的围栏配对不稳**
`lib/lint.js:18` `/```[\s\S]*?```/g`。复现 a：`"```js\nconst a = 1; // 首先，这是注释，其次，也是注释。综上，都是注释\nconsole.log(a);"`（未闭合）→ 代码未剥离，注释文字参与打分，**54 分**。复现 b：`"```js\nconst a = '```';\n```\n首先，结束语。综上所述。"` → 第一个 ` ``` ` 与代码字符串里的 ` ``` ` 提前配对，剩下的围栏错位（`chars=15`，仅 15 字幸存）→ **54 分**。
期望：未闭合时不误判，代码里的围栏不参与配对。实际：流式输出/截断输出、以及任何讨论 markdown 语法的文本都会被误判。**严重度：中**。建议：按"围栏必须独占一行（允许缩进）"匹配，未闭合时把余下内容判为代码。

**14. `both-sides` 命中正常汉语，且只覆盖一种连接词组合**
`lib/ruleset.js:76`。复现：`"他既不肯走，又不肯留，还天天抱怨，谁劝都没用。"` → 命中（25 分），这是人写口语；`"这个方案既有优点又有缺点，得看你怎么用。"` → 命中（`既有…又有` 分支）。两个方向都在打正常表达，而"既…又…"不带"还"的写法反而漏。
期望：只抓"一方面…另一方面"这类真正的两面陈述模板。实际：把 `既…又…` 一律当两面派。**严重度：中**。建议：只保留 `一方面…另一方面` 分支。

**15. 已验证但对靶子无害的项（攻击失败，如实记录）**
- `lastIndex` 复用：`lint.js:71` 用 `String.prototype.match(rule.re)`，`/g` 正则的 `lastIndex` 每次被 `match` 重置。实测同文本连跑 3 次，得分与命中签名完全一致（`70 / transition-cliche:2|not-x-but-y:1|summary-close:1|bold-density:1.11|bold-inline-label:1`），跑完 `RULES.filter(r=>r.re.lastIndex!==0)` 为空数组。**未打穿**。
- 灾难性回溯：5 组压力输入（39k 字"不是…而是…"重复、34k 字无标点、27k 字三项并列风暴、240k 字 400 行、51k 字混合真实文本）实测均值 1.4–22.1 ms，未发现指数级回溯。**未打穿**。
- 行内代码剥离：`"`首先，这是一个很好的问题，其次，综上所述` 这类字符串是模板。"` → 反引号内文本被正确剥离（`chars=9`、`score=0`）。**未打穿**。
- Tab 缩进 bullet：`"\t- 第一条"` 能正确计入 `bulletLines`。**未打穿**。
- 空文本 / 纯空白 / 纯代码块：均为 `score=0, chars=0, hits=[]`，无异常。**未打穿**。
- 开关语义：`planRegistrations({enabled:false}, …)` 与 `planRegistrations({level:"off"}, …)` 均返回 `null`；非法 level 回退 `strict`；`renderPrompt({level:"off"})` 返回 `""`。**未打穿**。
- 破折号变体：`——` 计 2 次触发 `emdash-density`；单独的 `—`（U+2014）与 `–` 不计入。属于规则覆盖窄，但 `emdash-density` 阈值下影响 ≤3 分，未单列为缺陷。

## 五、设计级质疑

**5.1 提示词可被一句用户指令绕过，且没有输出侧兜底**
证据：`index.js:59-62` 只做两件事——`ctx.systemPrompt.section(...)` 和 `ctx.tools.register(scanTool)`。全文没有任何针对 assistant 输出的拦截、后置校验或重试。`inject = ["systemPrompt", "tools"]`，没有引入输出过滤服务。`plan.js:26` 把段落挂在 `personaSuffix + 1`（实测补进 system prompt 的 order=101，位于系统提示末尾，但**仍在用户回合之前**）。
后果：用户消息在系统提示之后、优先级更高；一句"请用分点列表详细说明"就与提示词第 11 条（"低于 200 字不要列 bullet"）直接对撞，冲突时没有任何机制保证插件赢。`deai_scan` 是**建议性**的（`prompt.js:27` 只说"可以对草稿调用"），模型完全可以不调用。
建议：如果要的是"输出形态"，就得有输出侧校验（tool-call 后置钩子或 subagent 复核），纯系统提示只能算"倾向性引导"，不应在文档里表述为"抑制"。

**5.2 `deai_scan` 的自检提示会白烧 token，且没有任何预算约束**
证据：`injectLintTool` 默认 `true`（`index.js:18`），提示词写着"分数高于 35 时，按命中项重写"（`prompt.js:27`）。这意味着每一轮回答都可能多出一次"草稿全文入参 + 完整报告回传"的工具往返，命中后还要重写一遍。插件侧没有调用次数、频率或长度限制（`lint.js`/`index.js` 里没有任何计数器或缓存）。长回答时入参等于把答案再传一遍。
补充：`renderReport` 每次回传全部命中明细 + 最多 6 条建议，模型侧的平均额外消耗远高于一次普通工具调用。
建议：给 `deai_scan` 设"每次会话最多 N 次 + 文本长度上限"，或把自检降级为显式请求才触发；把"高于 35 重写"改成"只重写被标记的句子"。

**5.3 打分口径是自证循环**
证据：干预手段（`prompt.js` 的文字规则）、度量工具（`lib/lint.js`）、合格判据（"≥35 降到 <35"）三者来自同一个 `RULES` 数组。`docs/验收报告.md` 第 4.3 节"命中规则种类 13→5"就是这个循环的直接读数。
反证（实测）：把纯人写的样本喂给同一把尺子——FP-01 **57 分**、FP-10 33 分、HUMAN-LONG **43 分**、HUMAN-MID 25 分；而验收报告里被判定"达标"的注入组均值是 **16.3 分**。也就是说，**按同一把尺子，人写的中文比通过验收的模型输出更像'AI 腔'**。检测器测的是"是否命中我的词表"，不是"是否像人"。
建议：至少引入一个外部基准（人写语料打分分布），把合格线定义成"落入人写分布区间"而不是"低于我自己的分档边界"。

**5.4 会把中文文风压平**
证据：提示词第 1 条禁"此外"，第 4 条禁三项并列，第 8 条禁"一般来说/因人而异"，第 10 条把"维度/层面/体系/闭环/抓手/逻辑"列入替换名单。实测这些词在正常人写文本里都会命中（FP-01/FP-02/FP-03/FP-06/FP-08/D-17/D-06）。
后果：所有输出被推向同一种形态——短句、无连接词、无抽象名词、无序号、无列表。这本身就是一个模板，只不过换了个方向。插件目标是"去模板"，实际产出是"换成另一个模板"，而且这个模板拿掉了中文书面语里正常的连接与概括手段。
建议：把"禁用词"改成"密度阈值"——允许个别出现，只惩罚堆积（插件已经有 `sev` 和密度概念，却对 `sev3` 词用单次命中即 33 分的口径）。

**5.5 阈值 35 没有外部标定**
证据：35 是 `BANDS` 里 `slight/medium` 的边界（`lint.js:4-9`），同时被当成验收合格线；`prompt.js:27` 又把它当成"重写触发线"。三处复用同一个未经标定的数字。而这些分档的刻度由 `Math.max(chars, 300)` 与 `Math.min(count, 2)` 两个任意常数确定。
建议：把"分档"和"合格线"解耦；合格线用真实语料标定（例如人写样本的 95 分位）。
