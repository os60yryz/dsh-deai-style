## 一、结论速览

**失守 12 条：新误报 5 条、新漏报 4 条、口径/报告缺陷 3 条。**

按严重度排序的前三条：

1. **FN2-01（漏报，高）**：`service-close` 匹配不到「希望对你有帮助」。这正是 `index.js:25-27` 工具 description 点名的"客服式结尾"、也是 `lib/prompt.js:11` 写进系统提示的原句。实测 `lint("希望对你有帮助。")` 得 **0 分、0 命中**，正则子串测试 `false`。根因 `lib/ruleset.js:215` 的 `希望对(你|您)(有所)?帮助` 漏了裸 `有`。第一轮修 FP 时把主语限制去掉了，却没人跑过这个原句。
2. **FN2-02（漏报，高）**：**没有语言套话、只有排版特征的 AI 回答，恒得 0 分**。`lib/lint.js:191` 的 `metricBonus = ruleWeight === 0 ? 0 : ...` 让结构指标权重在没有任何规则命中时被整段丢弃。实测一个 143 字、含 2 个二级标题 + 2 处行首加粗的典型 AI 排版回答：`metricWeight = 8`、`score = 0`，报告结论是"基本没有 AI 腔"。这比第一轮刻意保留的"纯表格/纯列表"更普遍——只要 AI 换个说法不写套话，检测器就完全看不见它。6 个样例（纯标题层级、纯加粗提纲、纯编号步骤、纯 bullet、纯表格、标题+加粗+段落混排）全部 0 分。
3. **FP2-01（误报，中高）**：`emoji-marker` 是唯一的 `strong` 证据，独立定罪门槛只有"行首 emoji ≥2 行"。实测人类工作日志（3 行行首 emoji + 口语叙述）**45 分"中等 AI 腔"**，人类聊天 3 行 emoji **47 分**，2 行 emoji **35 分**。`lib/ruleset.js:312` 给出的理由"人类把 emoji 当 bullet 用在正式回答里极少见"在聊天/日志场景不成立。同一指标对 `1️⃣2️⃣3️⃣` 键帽 emoji 和 `🇨🇳` 区域指示符**完全失明**（0 命中 0 分，见 FN2-03）——同一个指标两头都错。

## 三、新失守

### 误报类

#### FP2-01 行首 emoji：人类聊天/工作日志被判「中等 AI 腔」

- 类别：误报
- 样例（`probe1` `B-WORKLOG`，46 字）：
  ```
  📌 今天把接口对完了
  ✅ 联调通过，明天提测
  ❌ 埋点方案还得再改一版
  路上地铁晚点，到公司快十点了。
  ```
- 期望：< 36（人写）　实测：**45 分 / 中等 AI 腔**
- 其它样例：`B-CHAT-EMOJI3`（19 字聊天）**47 分**；`B-CHAT-EMOJI2`（15 字聊天）**35 分**；`B-CHAT-EMOJI2-LONG`（76 字）32 分
- 命中规则：`emoji-marker(strong,sev2) x1.5`、`emoji-density(sev1) x1`
- 根因：`lib/ruleset.js:314` `measure: (t,m) => (m.emojiStartLines >= 2 ? scale(m.emojiStartLines/2, 1, 2) : 0)`；`strongScore` 在 `ruleWeight===0` 时仍独立成立（`lib/lint.js:189-190`），分母 `k = 4.5 + chars/100` 在短文下极小，2~3 行 emoji 就能推到 35~47 分。`lib/ruleset.js:312` 的理由（"人类极少这么做"）与聊天/工作日志场景不符。
- 建议修法：`strong` 独立定罪需要第二个条件——例如要求 `emojiStartLines / contentLines >= 0.5` 且 `contentLines >= 4`，或把独立定罪门槛提到 `emojiStartLines >= 4`。仅"≥2 行"不足以定罪。

#### FP2-02 人写学术摘要被判 62 分

- 类别：误报
- 样例（`probe1` `B-ACADEMIC`，205 字）：
  ```
  摘要：本文以2008—2020年A股上市公司为样本，考察数字化转型对企业全要素生产率的影响及其作用机制。研究发现，数字化转型显著提升了企业全要素生产率，该结论在运用工具变量法与倾向得分匹配法缓解内生性后依然稳健。机制检验表明，数字化转型主要通过降低信息不对称与优化资源配置两条路径发挥作用。进一步分析发现，该效应在国有企业与高新技术企业中更为明显。本文的研究结论为理解数字技术与实体经济深度融合提供了经验证据。
  ```
- 期望：< 36　实测：**62 分 / 明显 AI 腔**
- 命中规则：`buzzword(sev2) x3`、`colon-definition(sev1) x2`；`ruleWeight=6`、`metricWeight=2`
- 根因：`lib/ruleset.js:66` 把`数字化转型`列进黑话表——它在经管类论文里是**中性术语**，一篇摘要里出现 3 次极正常；`lib/lint.js:173-174` 的饱和曲线对重复命中不再线性摊薄，把 3 次命中抬到 60 分以上。饱和曲线修好了"长文免检"，同时放大了"同一术语重复出现"的误伤。
- 建议修法：给 `buzzword` 加"同一条目在同一文本内只计 1 次"的去重（按 `rule.id + 命中词` 去重），或把 `buzzword` 拆成"黑话"与"行业术语"两张表，后者不进 `RULES`。

#### FP2-03 半角「Key: value」被计入 `colon-definition`

- 类别：误报（轻度，只加成不定罪）
- 样例（`probe3` `colonEN`）：`"Install: npm i\nConfig: edit yaml\nBuild: npm run build\nTest: npm test\nDeploy: npm run deploy\nNotes: read the docs"`
- 期望：中文说明书指标不该被英文行喂饱　实测：`colon-definition x2`、`metricWeight=2`、score 0
- 根因：`lib/lint.js:43` 的排除集只写了全角 `，。！？；`，半角 `,` `;` `.` 不在其中，`[^\n：:，。！？；]{2,12}[：:]\s*\S` 于是把英文冒号行全数计入。反过来，纯半角标点串 `".,;:!?"` 也能命中 2 次（`probe2` `edge.punctOnlyHalf`）。
- 影响：任何"有 1 处中文规则命中"的技术文档会额外吃到最多 +4 分加成，把 33 分推过 36 线。
- 建议修法：`lib/lint.js:43` 排除集补半角 `,;.!?`，或将该指标限制在"冒号前为汉字"的行。

#### FP2-04 填表式回答被 `uplift-close` 误伤

- 类别：误报（轻度）
- 样例（`probe1` `B-FORM`）：`"问：为什么选择我们公司？\n答：贵公司在我所投递的岗位方向上积累深厚，与我的专业背景匹配度较高，我希望能在这里把学到的东西用起来。"`
- 实测：**18 分**，命中 `uplift-close(sev1) x1`（`lib/ruleset.js:245` 的 `希望(能|可以|你)` 分支）
- "我希望能…"是正常陈述，不是升华收尾。建议把该分支限定在 `scope: "closing"` 的最后一句，或要求与"未来/道路/明天"等词共现。

#### FP2-05 `~~~` 围栏与四反引号围栏：代码内容被当散文计分

- 类别：误报（同时是口径缺陷，见 BUG2-01）
- 样例（`probe2` `strip.fence_tilde`）：`"~~~js\n首先，综上所述，感谢大家的阅读。\n~~~"`
- 实测：剥离后 24 字全留，**65 分**（本应 0 字 0 分）
- 根因：`lib/lint.js:22-24` 只匹配反引号，CommonMark 合法的 `~~~` 围栏不在覆盖范围。`strip.fence4_nested_prose` 则因反引号数量硬编码为 3 而错配。
- 建议修法：开头围栏用 `^[ \t]*(`{3,}|~{3,})` 捕获围栏符与长度，闭合时匹配同符且长度 ≥ 开栏长度。

### 漏报类

#### FN2-01 `service-close` 匹配不到「希望对你有帮助」

- 类别：漏报（高）
- 样例：`lint("希望对你有帮助。")`、`lint("先说结论。\n\n希望对你有帮助。")`、`lint(结构化AI回答 + "\n\n希望对你有帮助。")`
- 期望：≥ 36（客服式结尾，sev 3）　实测：**三条全部 0 分、无 `service-close` 命中**
- 直接证据：`probe3` `serviceClose.substringCheck = false`（`/希望对(你|您)(有所)?帮助/.test("…希望对你有帮助。")` 返回 false）
- 根因：`lib/ruleset.js:215` 写成 `希望对(你|您)(有所)?帮助`，漏了裸 `有`。实际说法是「对你**有**帮助」/「希望这些内容对你**有**帮助」，两个最常见形式都匹配不上；只有别扭的「希望对您有所帮助」能命中。
- 影响面：`index.js:25-27` 的工具 description 把"客服式结尾"列为卖点，`lib/prompt.js:11` 也把"希望对你有帮助"写进禁止清单，检测器却对这句原话免疫。第一轮 FN-02 之所以"修好了"，是靠同段里的「以上就是…」「感谢大家的阅读」两个分支凑的分。
- 建议修法：`lib/ruleset.js:215` 改为 `希望[^\n。！？]{0,8}对(你|您)(有所|有)?帮助`，并补 `(以上|这些)(内容|信息)?(就)?(是|为)` 类变体；同时在 `tests/checks.mjs` 加一条单句断言锁死。

#### FN2-02 零语言套话、只有排版特征的 AI 回答恒得 0 分

- 类别：漏报（高，系统性）
- 样例与实测（`probe1`）：
  | 样例 | 字数 | metricWeight | 分数 |
  | --- | --- | --- | --- |
  | `C-STRUCT-ONLY` 标题+行首加粗+段落混排 | 143 | 8 | **0** |
  | `C-HEADING-ONLY` 纯六级标题层级 | 31 | 4 | **0** |
  | `C-BOLD-OUTLINE` 纯加粗提纲 | 30 | 4 | **0** |
  | `C-NUM-STEPS` 纯编号步骤 | 30 | 4 | **0** |
  | `C-BULLET-CLEAN` 带冒号定义的纯 bullet | 65 | 5.34 | **0** |
  | `C-TABLE-CLEAN` 纯表格 | 48 | 4 | **0** |
  | `FN2-03` 键帽 emoji 列表 | 78 | 0 | **0** |
- `C-STRUCT-ONLY` 全文（典型现代 AI 排版，零套话）：
  ```
  ## 结论

  先把结论放在前面：这件事值得做，但不要现在做。

  ## 理由

  **时机不对。** 团队刚经历一次大改版，现在启动第二个高风险项目，注意力会被切碎。

  **收益不明。** 目前没有数据能说明它能把转化率提高多少，全靠拍脑袋。

- 根因：`lib/lint.js:191` `const metricBonus = ruleWeight === 0 ? 0 : Math.min(4, metricWeight)` 与 `:189-190` `strongScore`（只认 `strong`）。所有 `format`/`rhythm` 指标在无规则命中时权重被**整体丢弃**，`metricWeight = 8` 不进分数。`lib/ruleset.js:259-260` 的注释还写着 format "可独立成立"，与实现相反。

- 建议修法：给 `format` 类开一条**有上限的独立通道**，例如 `formatScore = ruleWeight === 0 && formatWeight >= 6 ? Math.min(25, formatWeight * 2) : 0`，让"排版极端规整但语言干净"落到 20~25 分（`slight` 带），既提示模型又不至于误伤（第一轮实测换灯泡 52 分、会议纪要 52 分对应的 `formatWeight` 分别只有 3.7 与 2，不会触发）。

  ```
  1️⃣ 先把范围收窄。只覆盖一条业务线，两周跑完。
  2️⃣ 再定验收口径。谁来测、怎么算通过，提前写清楚。
  3️⃣ 最后才谈扩大。没拿到数据之前，不要承诺任何时间点。
  ```
- 期望：≥ 36（行首 emoji 当项目符号，正是 `emoji-marker` 的靶心）　实测：**0 分、0 命中、`metricWeight = 0`**
- 同类：`🇨🇳 中国\n🇯🇵 日本` → 0 命中；`1️⃣2️⃣3️⃣` 短样例 → 0 命中
- 根因：`lib/lint.js:39-40` 用 `\p{Extended_Pictographic}` 统计。键帽 emoji 的实际码点是 `U+0031 U+FE0F U+20E3`（数字 + 变体选择符 + 组合键帽，`U+20E3` 不是 pictographic），区域指示符 `U+1F1E8 U+1F1F3` 同样不在该属性内。于是这两种**最典型的"emoji 当 bullet"排版**既不算 `emojiStartLines` 也不算 `emojiCount`，而它们又匹配不上 `^[ \t]*(?:[-*+]|\d+[.、])` 的 bullet 正则，整个文本在指标层面是透明的。
- 建议修法：`lib/lint.js:39-40` 的匹配改成 `(?:\p{Extended_Pictographic}|\p{Regional_Indicator}{2}|\d\uFE0F?\u20E3)`；同时 `lib/lint.js:36` 的 bullet 正则补上键帽开头。

#### FN2-04 零宽字符插词即规避

- 类别：漏报 / 规避
- 样例（`probe3` `evasion`）：同一段 AI 腔 46 字
  - 原文：`首先，我们需要明确目标。其次，拆解任务。综上所述，这是一套行之有效的方法论。感谢大家的阅读。` → **80 分 / 明显 AI 腔**
  - 在「首先/综上/感谢」中间各插一个 `U+200B` → **45 分 / 中等 AI 腔**（`transition-cliche` 3→1、`service-close` 1→0）
  - 细空格 `U+2009`、软连字符 `U+00AD` 变体各得 70 分（部分失效）
- 根因：`lib/lint.js:19-28` `stripCode` 不做任何 Unicode 归一化（NFKC / 零宽剥离）；零宽字符还会被 `computeMetrics` 计入 `chars`（`lib/lint.js:31`），一并抬高 `k` 进一步压低分数。
- 影响：这是**对检测器本身的定向规避**，模型或用户只要在套话词里插一个不可见字符，规则就整条失效；而中文里插零宽字符在视觉上与正常文本无异。
- 建议修法：`stripCode` 开头加一步 `out.replace(/[\u200B-\u200F\u2060\uFEFF\u00AD]/g, "")`，并考虑 `String.prototype.normalize("NFKC")`。

### 口径 / 报告缺陷

#### BUG2-01 反引号数量硬编码导致四反引号围栏错配

- 类别：口径缺陷（同时造成 FP2-05）
- 样例（`probe2` `strip.fence4_nested_prose`）：
  `"````markdown\n```js\n首先，这是一个很好的问题\n```\n````\n综上所述，感谢大家的阅读。"`
- 实测剥离结果：`"\n\n首先，这是一个很好的问题\n\n\n综上所述，感谢大家的阅读。"`，`chars = 25`，`score = 65`
- 问题：外层 ````markdown 开栏与内层 ``` 被当成一对闭合，四行围栏被拆成两次不完整匹配，**内层代码正文（"首先，这是一个很好的问题"）泄漏进散文**并参与打分与字数统计。
- 根因：`lib/lint.js:22` `^[ \t]*```[^\n]*\n[\s\S]*?^[ \t]*```[^\n]*$` 无法区分 3 个与 4 个反引号。
- 建议修法：见 FP2-05。

#### BUG2-02 文末无换行的未闭合围栏残留反引号

- 样例：`"首先，明确目标。综上所述，感谢大家的阅读。\n```"`
- 实测剥离结果：`"首先，明确目标。综上所述，感谢大家的阅读。\n `"`，`chars = 22`（真实正文 21 字）
- 根因：`lib/lint.js:24` 的 `^[ \t]*```[^\n]*\n` 要求围栏行后有 `\n`，文件末尾的裸围栏匹配不上。影响很小（chars 虚高 1、分数不变），但属于 `stripCode` 与 `computeMetrics` 的字数口径不自洽。

#### REP2-01 `renderReport` 在 0 分时自相矛盾

- 类别：报告缺陷（用户可感知）
- 实测（`probe3` `reportZeroFull`，输入为 FN2-02 的 143 字结构化回答，`score = 0`）：
  ```
  AI 腔评分：0/100（基本没有 AI 腔）｜正文 143 字，命中片段 0 处（加权 0），规则密度 0/千字
  分类：结构节奏 8

  命中明细（按严重度排序）：
  - [结构节奏·2] bold-density ×2
  - [结构节奏·2] heading-ratio ×2

  改写建议：
  1. 加粗太多；一屏内最多留一处真正需要强调的。
  2. 小标题过密；短回答不需要分节。
  ```
- 问题：同一份报告里"0/100 基本没有 AI 腔"、"命中片段 0 处（加权 0）"和"分类：结构节奏 8"、两条 sev2 命中明细、"加粗太多/小标题过密"的改写建议同时出现。模型读到这段会收到互相矛盾的信号：分数说没事，明细说要改。
- 根因：`hits` 与 `byCategory` 收录了全部 metric 命中（`lib/lint.js:151-164`、`:235`、`:241-251`），而 `spans`/`ruleWeight`/`metricBonus` 只认被采用的部分（`:166-167`、`:191`）。报告没有标注"该指标未计入总分"。
- 建议修法：在每条 metric 命中后标注 `（format 类，未计入总分）`；`分类` 行改用与总分一致的权重口径；`score === 0 && hits.length > 0` 时补一句解释，例如"以下排版指标因缺少语言证据未计入分数"。

## 五、评分可信度与设计级质疑

### 5.1 确定性：通过

同一文本连跑 5 次（`probe2` `score.deterministic`），分数均 `78`，命中签名唯一（`sigs = 1`）。`collectSpans` 重建 RegExp 的做法（`lib/lint.js:95`）确实消除了 `/g` 的 `lastIndex` 污染。

### 5.2 分档边界：连续、无跳变，但语义偏松

`BANDS` = 15 / 35 / 60（`lib/lint.js:4-9`）。实测相邻样例：11 字 20 分 → 19 字 35 分 → 29 字 47 分 → 40 字 56 分，无跳变或死区。问题在于**档位语义与检测能力不匹配**：`0/100（基本没有 AI 腔）` 这个结论同时出现在"纯空白"和"143 字高度结构化的 AI 回答"上（FN2-02）。分数为 0 时报告给出的是一句无条件的正面结论，缺少"仅基于词表与已知指标、不代表文本自然"的限定。

### 5.3 分数可被单句反向操纵（加一句套话就跨档）

`probe2` `score` 实测同一份 143 字的干净结构化回答：

| 变体 | 分数 | 档位 |
| --- | --- | --- |
| 原文（零套话） | 0 | clean |
| 追加「综上所述，这就是全部内容。」 | 19 | slight |
| 追加「这不是时间问题，而是决心问题。」 | **43** | **medium** |
| 追加「希望对你有帮助。」 | **0**（服务端漏报，见 FN2-01） | clean |

同一段文字，加一句 `not-x-but-y` 就从 0 跳到 43——因为 `metricWeight = 8` 在此之前一直被丢弃，一旦 `ruleWeight > 0` 就整段解锁并封顶 +4。这不是"密度打分"，是**开关打分**：分数由"有没有踩到词表"决定，排版证据只是开关上的附加项。往文章里塞一句无害套话能让分数从 0 冲到 43；反过来，把 AI 文拆成多段（`probe2` `joined` / `joined_blanklines` / `joined_samepara` 三种分段方式）**分数完全不变（均 46）**，说明分段拆分不影响判定——这一条攻击没打穿。

### 5.4 提示词可被一句用户指令绕过（未实测，仅静态论证）

- 静态事实（`probe3` `promptBypass`）：`lib/prompt.js:19` 的"不要列 bullet"只在 `strict` 档存在，且限定条件是"低于 200 字的回答"；`lib/prompt.js:31` 的 `soft` 档完全不包含这条。
- `index.js:50-63` 的 `apply()` 只做 `ctx.systemPrompt.section()` 与 `ctx.tools.register()`，没有任何 `llm/stream`、`assistant-stream` 或输出改写钩子。`round1-fix.md` §七.1 对此的判断（"模型可以被『请用分点列表详细说明』这类指令绕过"）**属实**。
- 后果可量化：等价产出（`probe3` `keycap` / `promptBypass`）——`"以下是三种方法：\n- 番茄工作法…"` 得 **0 分**，而它正是"请用分点列表详细说明"这类指令的典型产物。即：**注入的约束要么被用户指令压过，要么即使模型照做也测不出来**。
- **明确标注：本节未做真实模型调用实测。** 原因：本会话网络受限、未持有可用的模型 API 凭据（凭据型环境变量在工具壳中被擦除，见全局规范 §28），且任务约束禁止为此消耗预算。以上仅为 `lib/prompt.js` 与 `index.js` 的静态阅读结论。

### 5.5 `deai_scan` 工具 description 的准确性

`index.js:24-27` 声称覆盖四类特征，逐条核对：

| 声称 | 核对结果 |
| --- | --- |
| "模板连接词（首先/其次/综上所述）" | ✅ 准确 |
| "对偶反转句（不是X而是Y）" | ✅ 准确（FN-07 实测 71 分） |
| "「- **小标题**：内容」式列表" | ✅ 准确（FN-08 实测 95 分） |
| "空洞夸饰词" | ✅ 准确（`empty-grandeur`） |
| **"客服式结尾等 AI 腔特征"** | ❌ 不准确。最典型的"希望对你有帮助"实测 0 分（FN2-01）。description 把一个当前不成立的检测能力写成了卖点 |
| "只做诊断，不改写文本" | ✅ 准确（`renderReport` 只输出建议文本，不返回改写后文本） |

### 5.6 设计级：度量尺与干预依据同源

`round1-fix.md` §七.2 自认"打分口径自证循环"，本轮实测加重了这一判断：`metricBonus` 的开关（`ruleWeight > 0`）与 `RULES` 词表完全同源，导致分数只反映"踩了几条词表"，不反映"读起来像不像 AI"。FN2-02 的 6 个样例是直接证据——它们在人类读来是最典型的 AI 排版，在系统里得 0 分。阈值 35 因此也没有外部标定基础（§七.3 自认）。
